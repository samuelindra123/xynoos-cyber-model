# TASK 004 — Dataset Governance and Streaming Specification

**State:** TASK 004-A planning contract; no dataset pipeline implementation or external corpus acquisition is included.

## 1. Provenance-first acquisition and governance

The project must authorize each source before acquisition or use. Public availability alone is not permission to train or redistribute. A source registry entry must identify: stable source ID; original URL or lawful acquisition reference; source version/revision; acquisition date (UTC date); checksum of acquired source material; applicable license and version; terms-of-use reference; independently recorded permitted training use; redistribution permission and conditions; transformation history; domain classification; responsible maintainer role/handle; review status and review date. Record `unknown` only in an intake/quarantine record, never in an accepted training manifest. Review must distinguish source-code license, dataset license, model-weight license, software dependencies, and project Apache-2.0 code license.

Never collect or publish credentials, API keys, personal information, private-repository contents, unauthorized proprietary material, restricted content, or illegally obtained datasets. Cyber material must be lawful and suitable for defensive, educational, or explicitly authorized research. Do not acquire large external data in TASK 004. The first experiment uses project-authored synthetic fixtures. An individual sample cannot become approved by copying it from a public page; record and review its applicable terms first.

For all categories: content checksum and immutable revision, reproducible acquisition process, explicit privacy review, exact and later near-duplicate analysis, quality review, documented transformations, split leakage analysis, and an appeal/removal path are required. A data provenance manifest does not itself convey legal rights.

## 2. Record, source registry, and dataset manifest

Use UTF-8 JSON Lines (`.jsonl`) with one canonical JSON object per line, LF terminator, no blank lines, no duplicate keys, and deterministic object-field order. JSON is inspectable and incrementally parseable. The workspace should use a pinned `serde`/`serde_json` implementation with an explicit struct field order and a canonical serializer; maps with unspecified iteration order are prohibited. Canonicalization must be documented and tested with exact bytes. No JSON value may exceed configured byte limits. New schema versions require explicit code and compatibility review; unknown major versions are rejected.

Three logical files may live beside a dataset outside Git: a source registry, a document manifest, and immutable document payload files. They use relative normalized `/` paths only and are not required to store all corpus text in Git.

Source registry record (`schema_version=1`) includes `source_id`, `source_reference`, `source_revision`, `acquired_utc_date`, `source_sha256`, `license_id`, `license_version`, `terms_reference`, `training_permission` (explicit enum), `redistribution_permission` (explicit enum/conditions), `transformation_history`, `domain`, `responsible_maintainer`, `review_status`, `reviewed_utc_date`. Accepted statuses are `approved` only; `pending` and `rejected` records cannot feed training. Terms/reference fields may point to public URLs or an access-controlled lawful local review record identifier, but never machine-specific absolute paths or credentials.

Each document manifest record (`schema_version=1`) includes `document_id` (stable opaque ASCII ID), `source_id`, `source_revision`, `payload_path` (relative), `content_sha256` (SHA-256 of exact payload bytes), `byte_length`, `encoding` (`utf-8` only in v1), `domain_labels` (sorted unique controlled labels), `split` (`train`, `validation`, `test`), `cleaning_status`, ordered `transformation_ids`, `tokenizer_compatibility` (tokenizer format/algorithm ID or `unassigned` before tokenization), and `duplicate_group_id` (stable ID after exact-dedup grouping). Required provenance is resolved against an approved source-registry record; training rejects unresolved provenance.

Payload is exact UTF-8 document content with no implicit terminal newline. `byte_length` and `content_sha256` describe the payload bytes, not parsed/reformatted text. A UTF-8 BOM is not silently stripped; v1 rejects it unless a named transformation has explicitly removed it and recorded the before/after checksums. Newline bytes, tabs, and all whitespace are preserved unless an authorized transformation explicitly changes them.

Manifest integrity is a separate deterministic sidecar: `manifest.json` contains schema version, dataset ID/version, tokenizer ID, split algorithm/version/seed, ordered record count, and SHA-256 of exact canonical `documents.jsonl` bytes and `sources.jsonl` bytes. Define `dataset_id` as lowercase hex SHA-256 of `b"XYNOOS-DATASET-V1\\0" || u64_be(source_jsonl_byte_length) || source_jsonl_exact_bytes || u64_be(document_jsonl_byte_length) || document_jsonl_exact_bytes`; lengths are unsigned 64-bit big-endian, all concatenation is byte-exact. Because each document row commits its payload checksum, this commits to the selected payload set without reading payload bytes to derive identity. Each payload has its own checksum. A manifest checksum is not an authenticity claim.

Reject malformed JSON, duplicate keys, duplicate document/source IDs, unsupported schema versions, missing required fields, missing/unapproved provenance, invalid dates or enum values, non-normalized/absolute/parent-traversal paths, absent payloads, incorrect byte length/checksum, invalid UTF-8/BOM without transformation, empty or oversized content when policy rejects it, unrecognized transformations/domains, and any record above the configured caps. Rejection diagnostics expose safe metadata only: file/record ordinal, stable ID when available, error code, lengths and checksums where safe. Never log or echo original payload text on failure.

## 3. Explicit preprocessing and privacy stages

Processing is staged and versioned: source intake and rights review; raw checksum; format/type and encoding validation; sensitive-content screening; transformation (only named authorized transforms); exact duplicate grouping; quality review; deterministic split; training tokenizer fit on train only; streaming tokenization. Every transformation records its ID/version, parameters, responsible process, and input/output checksum. Tokenization is not a cleaning step. For document token streams, the default boundary grammar is optional BOS at position zero, zero or more ordinary byte/BPE tokens, optional EOS as the final position. DOC_SEP is excluded from this grammar and is accepted only under a future explicit packed-document policy. PAD is excluded from stored documents and accepted only as a contiguous batch suffix with a corresponding false validity/loss mask. Literal marker text remains byte tokens.

Exact duplicate detection uses SHA-256 over exact bytes and groups identical documents before split assignment. Hash equality is used for grouping; if a cryptographic collision is suspected, compare bytes before treating content as identical. Near-duplicate detection is not a TASK 004-B requirement; it is future research, with method/version and false-positive/negative assessment required before cross-corpus claims.

Screeners can use bounded patterns/heuristics for likely credentials, keys, personal information, binary payloads, and low-quality text, but they are not guarantees of privacy or completeness. High-risk sources require human review and conservative exclusion. Binary content is rejected from the UTF-8 dataset API, while arbitrary binary round-trip belongs only to tokenizer byte tests. Empty, invalid, oversized, sensitive, or malformed records are discarded from accepted datasets; a separate safe rejection ledger can retain IDs, source ID, checksum, byte length, stage, and error code, but not original content, secrets, or sensitive excerpts. A filtering score or passing scan never proves a document contains no private data.

Preserve source-code syntax, indentation and whitespace. Any normalization, redaction, removal, or formatting conversion must have documented authorization, deterministic code/version, explicit parameters, audit trail and checksums. Privacy deletion requests require tracing source/derived document IDs and regenerating downstream manifests/artifacts as appropriate.

## 4. Deterministic split and tokenizer fit

Split documents, not lines, chunks, or tokens. Exact duplicates are grouped before splitting. Default v1 assignment hashes `split_version || NUL || seed || NUL || group_id` with SHA-256 and maps the first 64 bits, big-endian, to fixed thresholds: `[0, 80%)` train, `[80%, 90%)` validation, `[90%, 100%)` test. Percent comparisons use integer arithmetic, never floating point; version 1 fixes these boundaries. An optional source-grouped policy uses source ID as group key for sources whose versions/related docs could leak; it is a different named/versioned split algorithm and must be selected before assignment. The manifest records algorithm name, version, seed, group key policy, record order, and resulting split per document.

Before acceptance, validate unique IDs, exact-duplicate groups confined to one split, source-grouping constraints, expected split counts, stable re-assignment under input reordering, and a cross-split checksum/duplicate scan. Evaluation questions and answers must remain held out. Exact deduplication will miss normalized, modified, translated, or semantically overlapping text; report that limit and consider future near-duplicate and human overlap review.

Tokenizer vocabulary and BPE merges are trained exclusively on `train` records authorized for training. The training API receives a train-split iterator; it must reject validation/test records if split metadata is available. The resulting tokenizer artifact records dataset ID and training split manifest checksum as fit provenance. A tokenizer fit on held-out evaluation content invalidates that evaluation.

## 5. Bounded streaming and error semantics

The reference reader processes manifest entries in canonical deterministic order, validates one record and payload at a time, tokenizes one document at a time, then yields bounded batches. It never loads a corpus or all tokens into RAM. It may use `BufRead` with a configurable buffer, incremental line parsing, checked record byte limits and fallible owned buffers. Queue capacity is 1 in the reference implementation (synchronous producer/consumer); a future bounded queue requires explicit capacity and owned-byte accounting. Parallel nondeterministic ingest is out of scope.

Manifest order is stable and explicit; never depend on filesystem enumeration or hash-map order. Batching is deterministic for a fixed manifest, split, tokenizer artifact, sequence configuration and seed. The first implementation can read local files synchronously. It must distinguish normal end-of-stream from truncated final JSONL line, malformed record, absent file, I/O error, cancellation, and limit exhaustion. A partial final record is an error, not a quietly dropped record. On early termination or error, iterators release owned buffers and file handles when dropped; diagnostics do not expose text. No retry changes ordering silently. Re-running from the same manifest/config yields the same sequence and batch IDs.

Accounting includes configured reader buffer, one serialized record buffer, one decoded document buffer, one document token buffer, bounded merge/encoding scratch, current batch inputs/targets/masks, and any queue-held owned payload. It excludes caller-held records, memory maps unless explicitly accounted, allocator/OS overhead, thread stacks and other process allocations. Report configured and observed application-owned capacity estimates; do not claim exact RSS control. The iterator API should return `Result<Option<Batch>, DatasetError>` (or equivalent), with `None` only for clean end-of-stream.

## 6. Next-token samples and document boundaries

For a document token stream including explicitly configured boundaries, an input window `[t0, ..., t(L-1)]` has target `[t1, ..., tL]`, with exact one-position shift and equal lengths. IDs are integer `u32`. For sequence length `L`, input and target shape are `[L]` per sample or `[B,L]` for a batch. Validate every ID against the selected tokenizer vocabulary before yielding.

Default document policy is `PerDocument`: windows do not cross documents. Include BOS/EOS only when configured explicitly. A final unpaired token can be dropped, or EOS can serve as the final target if the document policy inserted it; record which policy is selected. Do not silently concatenate unrelated documents. An explicit later `PackedWithSeparator` policy may fill windows across documents only by inserting `DOC_SEP` or EOS and setting a loss mask that states whether boundary tokens contribute. The default is no packing.

Window stride is an explicit integer `1..=L`; default stride is L (non-overlapping windows), with any tail shorter than required dropped and counted. A partial final batch is yielded with actual `B`, unless fixed-size padding is explicitly requested. Padding uses PAD ID, never zero as a substitute, and emits a boolean/byte valid-token mask; padded input positions and targets have loss-mask false. Without padding, all masks may be omitted or all-true as a documented batch convention. PAD is forbidden inside unpadded content. Invalid zero sequence length, zero batch size, stride greater than length, batch token count above cap, inconsistent masks, unknown IDs, or arithmetic overflow is a typed configuration/data error.

Batch accounting includes input IDs, target IDs, optional attention/loss masks only if those are later defined by a consumer, and temporary assembly capacity. TASK 004 does not implement an attention mask. For planned data batches, include `B*L` inputs plus `B*L` targets; padded tensors require explicit padding mask and loss mask semantics. No floating-point token storage.
