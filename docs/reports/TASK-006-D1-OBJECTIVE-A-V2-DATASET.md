The split is assigned by the checked-in versioned SHA-256 group algorithm, not by trusting a supplied split label. Operand ranges are separated by split, and the independent task-index audit finds no repeated input combination across train, validation, and test. It independently recomputes every task answer, verifies that the answer occurs once after its inputs, and checks the answer end against byte spans expanded from the full-sequence BPE tokens. All 48 answer ends align to an actual token boundary by target position 31 or earlier. However, **8 of 48 answer starts fall inside a BPE token** because the preceding delimiter and `odd` are merged. The current evaluator reports whole-sequence loss and does not mask to an answer-only target span; this corpus therefore cannot support an answer-only loss or accuracy claim. BPE fitting uses all 24 train rows and no held-out row; a separate standard-library implementation reproduces the exact tokenizer artifact.

## Leakage and evaluation limits

The audit finds no normalized exact cross-split duplicate. It does find **23 cross-split pairs above the fixed 0.82 character-trigram Jaccard threshold**, with a maximum of 0.930233. The repeated templates make this expected and still material: these 48 records do not provide independent language coverage. The test split is public and visible in the repository, so it is not a secret holdout. The task-index check catches exact operand-combination overlap, but it cannot establish broad compositional generalization.

This is Objective A only: a small deterministic software control over three authored arithmetic tasks. It does not measure cybersecurity knowledge, Objective B technical-corpus learning, or general reasoning. Twelve examples per task family in validation and test are descriptive, not powered estimates. A separate human data-quality review remains required before admitting this corpus to an authorized experiment.
